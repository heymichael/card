Card Authentication and Access Control Requirements

This document defines business and product requirements for phase 1 authentication across the card app and docs surfaces, including sign-in flow, authorization policy, and deploy/runtime auth contract inputs needed for stable platform integration.

1. Objectives

  • Require authenticated access to the app and docs surfaces for approved users only.
  • Support Google-only sign-in with predictable allowlist-based authorization.
  • Define runtime auth contract inputs early so deployment integration does not need rework.

2. In Scope

  • Client-side authentication for app and docs in this repository.
  • Shared sign-in session across this app/docs pair with separate allowlists per surface.
  • Phase 1 deploy/runtime auth contract documentation and validation expectations.

3. Out of Scope

  • Cross-app single sign-on in the broader Haderach environment.
  • Server-side docs auth enforcement in this phase.
  • IAP integration in this phase.

4. Functional Requirements

IDRequirementPriority
FR-AUTH-01 The system must support Google-only login using Firebase Authentication. Must
FR-AUTH-02 The app and docs must share sign-in state within this repository while enforcing separate allowlists for app authorization and docs authorization. Must
FR-AUTH-03 Authorization checks must support both per-user email allowlists and per-domain allowlists, using case-insensitive matching. Must
FR-AUTH-04 Unauthorized users must remain signed in but see a blocked/login screen with a generic "contact administrator" message and a sign-out action. Must
FR-AUTH-05 Local development must support authentication by default and optional bypass for both app and docs together through a single explicit developer flag. Should

5. Non-Functional Requirements

IDRequirementPriority
NFR-SEC-01 Production auth config failure modes must fail closed (deny access). Must
NFR-OPS-01 Runtime auth configuration must come from deploy env vars and local .env.local. Must
NFR-UX-01 Transient auth failures must present a retryable message and preserve blocked state until successful authentication. Must

6. Acceptance Criteria

  • Allowed users can sign in with Google and access app and docs according to per-surface policy.
  • Non-allowlisted users can sign in but are blocked with contact-administrator guidance.
  • Case-insensitive email/domain matching works as specified for app and docs checks.
  • Missing/invalid production auth config blocks access and surfaces clear failure messaging.
  • Local auth bypass flag can disable auth checks for both surfaces when explicitly enabled.

7. Deploy and Runtime Auth Contract Inputs (Exact Detail)

This section reproduces the exact detail list finalized in planning:

  • Auth stack: Firebase Auth with Google provider (Google-only sign-in UX)
  • Scope: one shared sign-in session for this app/docs pair only (not cross-app SSO)
  • Authorization model: separate allowlists for app vs docs
  • Initial allowlisted users (both): michael@haderachi.ai, michael@heretic.fund, mariam@heretic.fund, mariam@heretic.ventures, alexmader@gmail.com
  • Initial allowed domains (both): haderach.ai
  • Matching rules: case-insensitive; exact domain match only (wildcards later)
  • Unauthorized behavior: remain signed in, show blocked/login screen with generic "contact administrator" message + sign-out option
  • Failure policy: fail closed in production for missing/invalid auth config
  • Transient auth errors: show retryable login error; keep blocked
  • Environments: local + prod now (preview/staging same model when introduced)
  • Local dev: auth enabled by default, optional single bypass flag for both app and docs
  • Config source of truth: deploy env vars + local .env.local
  • Ownership: you own auth config/rotation
  • Platform assumptions: no IAP in this phase; docs server-side auth deferred; current enforcement is client-side
  • Session policy: default Firebase persistence for phase 1

8. Risks, Rollback, and Follow-Ups

  • Risk: Client-side checks alone do not replace server-side enforcement for sensitive docs.
  • Risk: Incorrect allowlist entries can block intended users or over-allow access.
  • Rollback: Disable auth gate via controlled config rollback only if emergency access is required.
  • Follow-up: Add wildcard domain support and server-side docs authorization in next phase.
