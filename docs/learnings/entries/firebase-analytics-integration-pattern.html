Firebase Analytics Integration Pattern

This learning captures how to add Firebase Analytics to an authenticated app with environment-gated initialization, per-page-load event deduplication, and dev console logging for pre-deploy verification.

Problem

The app had Firebase initialized for authentication but no analytics. The measurement ID was present in the Firebase config but getAnalytics() was never called, so no data appeared in Firebase Analytics or GA4 dashboards. Adding analytics required decisions across multiple dimensions: which SDK to use (Firebase SDK vs gtag.js vs GTM), when to initialize (before or after auth), how to avoid polluting production data during development, how to deduplicate high-frequency UI events, and how to verify instrumentation locally without deploying.

Reusable Pattern

  • Single analytics module: Encapsulate all analytics logic in one module (src/analytics/analytics.ts) that owns initialization, environment gating, event deduplication, and named track functions. Components call simple typed functions (e.g., trackFontFamilyChanged(block, font)) without knowing about Firebase internals.
  • Pre-auth initialization: Call getAnalytics(app) immediately after initializeApp(), before the auth gate renders. This captures the full funnel: page view → sign-in → feature usage → conversion. Set setUserId() after successful auth to link pre-auth events retroactively.
  • Production-only with dev console logging: Gate analytics on import.meta.env.DEV and auth bypass flags. In dev mode, log events to the browser console with event names, parameters, and dedup status instead of sending to Firebase. Vite dead-code-eliminates the dev paths from production builds.
  • Per-page-load deduplication: Use an in-memory Set<string> keyed by event name. High-frequency interactions (slider drags, keystrokes) fire once per page load. Conversion events use two names: one that always fires (volume) and one that deduplicates (conversion rate).
  • Firebase SDK over gtag.js: When Firebase is already in the app, use the Firebase SDK for analytics rather than adding a separate gtag.js script. Both write to the same GA4 property. One SDK, one init flow, no duplication.
  • Hardcoded event names: Each event has an explicit string constant in the analytics module, not derived from DOM elements or button text. This decouples analytics from UI structure and makes the event catalog readable in one file.

Proposed Template Change

  • Add a standard src/analytics/ directory to the template with a skeleton analytics module that includes the environment gating, dedup, and dev logging patterns.
  • Wire initAnalytics(app) into the auth gate template after initializeApp().
  • Include docs/analytics-strategy.md as a decision-record template covering Firebase SDK vs gtag.js vs GTM rationale, event specification format, and GA4 custom dimension registration requirements.
  • Document the dev console logging pattern as the standard pre-deploy verification approach for analytics changes.

Risk and Rollout Notes

  • Custom dimensions require manual GA4 registration: Event parameters automatically flow to BigQuery but must be registered in GA4 Admin → Custom definitions to appear in Firebase/GA4 console reports. Registration is not retroactive in the console.
  • BigQuery export is not retroactive: Enable early in Firebase Console → Project Settings → Integrations. Only captures events from the enable date forward.
  • GA4 parameter limits: 100-character string value limit, 25 parameters per event, 500 distinct event names per property. Truncate long text values before sending.
  • Small user base thresholding: GA4 applies data thresholding when it believes individual users could be identified. BigQuery export avoids this with raw unthresholded data.
  • Bundle size: The firebase/analytics module adds ~20–30 KB. For apps already using Firebase, this is marginal. For lightweight apps without Firebase, gtag.js has a smaller footprint.
