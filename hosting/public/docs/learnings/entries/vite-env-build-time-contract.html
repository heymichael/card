Vite Env Build-Time Contract

This learning captures the requirement that Vite VITE_* environment variables must be present in two places — local .env.local for development and GitHub repository secrets for CI/production builds — and the failure modes when this contract is broken.

Problem

Vite inlines import.meta.env.VITE_* values at build time as static string replacements. If a variable is present in .env.local but not passed to the CI build step, the production bundle receives undefined for that value. This creates a class of bugs that only manifest in production:

  • Local works, production breaks: The developer has all values in .env.local, so the app works locally. But the CI build step in publish-artifact.yml only passes variables that are explicitly mapped from GitHub secrets. Any variable not mapped is silently undefined in the production bundle.
  • Silent failures: Missing optional values (like VITE_FIREBASE_MEASUREMENT_ID) don't cause build errors. The app loads and runs but features that depend on those values (like analytics) silently fail. There is no build-time or runtime error to surface the gap.
  • Incomplete secret propagation: When a new VITE_* variable is added to .env.example and .env.local, the developer must also add a matching GitHub repository secret and map it in the workflow env: block. This is a manual two-step process with no automated check.

Reusable Pattern

  • Single source of truth: Treat .env.example as the canonical list of all VITE_* variables the app uses. Every variable listed there must exist in three places: .env.example (documentation), .env.local (local development), and GitHub repository secrets (CI builds).
  • Explicit workflow mapping: In the CI workflow's build step, explicitly map every VITE_* variable from secrets to environment, including optional ones. If a secret is not set in GitHub, the value will be empty rather than the variable name being absent — this is safer and makes gaps visible.
  • New variable checklist: When adding a new VITE_* variable:
    1. Add to .env.example with a blank or example value.
    2. Add the real value to .env.local (not committed).
    3. Create a GitHub repository secret with the production value.
    4. Map the secret in the workflow env: block for the build step.
  • GitHub secrets for all VITE_ values: Even non-sensitive identifiers like project IDs should be stored as repository secrets (not variables) for consistency. This avoids a split mental model where some values are secrets and some are variables.

Proposed Template Change

  • Add all .env.example entries to the publish workflow build step's env: block, mapping each from ${{ secrets.VARIABLE_NAME }}. Include optional variables so they are present (even if empty) rather than absent.
  • Add a comment in .env.example noting that each variable must also be set as a GitHub repository secret and mapped in the CI workflow.
  • Document the new-variable checklist in README.md under the authentication configuration section.
  • Consider a CI pre-build check that compares .env.example keys against the workflow's env: block to catch unmapped variables before they reach production.

Risk and Rollout Notes

  • No build-time validation: Vite does not error on missing VITE_* values. A CI check or runtime startup validation is the only way to catch gaps before users do.
  • Secret rotation: When rotating Firebase credentials or API keys, both .env.local and GitHub secrets must be updated. Forgetting the GitHub secret causes the next production build to ship with stale or empty values.
  • Debugging difficulty: Because values are inlined at build time, inspecting the production bundle (or the Network tab) is the only way to confirm what values were actually baked in. There is no runtime config endpoint to check.
