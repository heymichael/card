1. Purpose & Business Context

1.1 Problem Statement

Users who want to create personalized greeting cards currently face two poor options: (a) use expensive, feature-bloated design software that requires training, or (b) use online services that impose templates, watermarks, subscriptions, or require account creation. There is no lightweight, free, instant tool for creating a simple custom greeting card with personal text and a photo.

1.2 Proposed Solution

Build a browser-based greeting card designer that lets a user create a print-ready personalized greeting card in under two minutes, with no account, no server, and no cost. The tool should feel as simple as filling out a form, while producing output suitable for professional printing at standard card dimensions.

1.3 Business Objectives

  • Enable non-technical users to produce a custom greeting card with zero onboarding.
  • Produce print-quality output (300 DPI at standard card size) without requiring the user to understand print specifications.
  • Operate entirely client-side with no backend, eliminating hosting costs, data privacy concerns, and account management.
  • Serve as a technology prototype demonstrating interactive canvas-based editing with React and Konva.js.

1.4 Target Users

  • Primary: Non-designers who want to make a one-off personalized card (birthday, thank-you, congratulations) and either print it at home or send the image digitally.
  • Secondary: Developers evaluating Konva.js / HTML5 Canvas for interactive design tools.

1.5 Success Criteria

  • A first-time user can produce and export a finished card within 2 minutes.
  • Exported JPEG is exactly 1500 × 2100 pixels (5″ × 7″ at 300 DPI), suitable for commercial print services.
  • The application loads and runs entirely in the browser with no server round-trips after initial page load.

2. Scope

2.1 In Scope

  • Single-page web application for desktop browsers.
  • Two editable text blocks (headline and message) with full typographic controls.
  • Optional photo upload with positioning and resizing.
  • Card background color customization.
  • Curved and wavy text rendering.
  • JPEG export at print resolution.
  • Keyboard shortcuts for precision positioning.

2.2 Out of Scope

  • User accounts, authentication, or cloud storage.
  • Server-side rendering or processing.
  • Multi-page cards (front/back/inside).
  • PDF export or direct print integration.
  • Undo/redo history.
  • Mobile-optimized layout.
  • Stock image library or clip art.
  • Multiple card size presets.

3. Functional Requirements

3.1 Card Canvas

IDRequirementPriority
FR-CAN-01 The application shall display a visual canvas representing a 5″ × 7″ greeting card at 300 DPI (1500 × 2100 pixels). Must
FR-CAN-02 The canvas shall scale responsively to fit the available browser viewport while maintaining the card's aspect ratio. Must
FR-CAN-03 The canvas shall respond to browser window resizes in real-time. Should
FR-CAN-04 The canvas shall display a subtle drop shadow to visually distinguish the card from the workspace background. Could
FR-CAN-05 The user shall be able to toggle the display of safe-margin guide lines (0.25″ / 75px inset from each edge) to indicate the printable area. Should

3.2 Background Color

IDRequirementPriority
FR-BG-01 The user shall be able to select a background color for the card using a color picker control. Must
FR-BG-02 The default background color shall be a very light pink (#fff0f3). Must
FR-BG-03 The background color shall render behind all other content (photos and text). Must
FR-BG-04 The background color control shall be clearly labeled so the user understands it affects the card background, not the text. Must
FR-BG-05 The control shall display the selected hex value and a preview swatch. Should

3.3 Text Editing

IDRequirementPriority
FR-TXT-01 The application shall support exactly two text blocks: a headline (Block A) and a message (Block B). Must
FR-TXT-02 The user shall be able to switch between text blocks using clearly labeled tab-style buttons in the controls panel. Must
FR-TXT-03 Each text block shall support editing of: text content (multi-line), font size, font family, text color, and horizontal alignment (left, center, right). Must
FR-TXT-04 Font size shall be adjustable via both a range slider (20–200px) and a direct numeric input (10–400px). Must
FR-TXT-05 The application shall provide a selection of at least 10 system fonts. No custom font loading is required. Must
FR-TXT-06 Text color shall be selectable via a native color picker, with the current hex value displayed. Must
FR-TXT-07 The selected text block shall display a dashed blue selection box on the canvas to indicate which block is active. Should
FR-TXT-08 Clicking or tapping a text block on the canvas shall select it and update the controls panel to reflect that block's properties. Must

3.4 Curved Text

IDRequirementPriority
FR-CRV-01 Each text block shall support a curved rendering mode where text follows an SVG path instead of rendering on a straight line. Should
FR-CRV-02 The application shall support at least two curve types: a circular arc and a wavy bezier (sine-wave-like path with multiple direction changes). Should
FR-CRV-03 The curve depth/amplitude shall be configurable per text block. Should
FR-CRV-04 Default configuration: the headline shall use an arc curve; the message shall use a wavy bezier curve. Could

3.5 Positioning & Drag

IDRequirementPriority
FR-POS-01 Text blocks shall be repositionable by clicking and dragging on the canvas. Must
FR-POS-02 Text blocks shall be constrained so they cannot be dragged outside the card boundaries. Must
FR-POS-03 Arrow keys shall nudge the selected element by 1 pixel. Shift+Arrow shall nudge by 10 pixels. Should
FR-POS-04 Keyboard nudging shall be suppressed when a form input (text field, select, etc.) has focus, to prevent conflicts with normal text editing. Must
FR-POS-05 A "Reset Positions" button shall restore all elements (text blocks and photo) to their default positions. Should

3.6 Photo

IDRequirementPriority
FR-PHO-01 The user shall be able to upload a photo from their local device. Accepted formats: JPEG, PNG, WebP. Must
FR-PHO-02 The uploaded photo shall be initially scaled to fit the card width and vertically centered. Must
FR-PHO-03 The photo shall render behind text blocks but in front of the background color. Must
FR-PHO-04 The photo shall be repositionable by dragging. Unlike text, the photo may extend beyond card boundaries (content is clipped to the card edge). Must
FR-PHO-05 The photo shall be resizable via drag handles (Konva Transformer) while maintaining its aspect ratio. Must
FR-PHO-06 The photo shall not be resizable below 20 × 20 pixels. Should
FR-PHO-07 The user shall be able to replace the current photo with a new one. The button label shall change from "Add Photo" to "Replace Photo" when a photo is present. Should
FR-PHO-08 The user shall be able to delete the photo by pressing Delete or Backspace when the photo is selected. Should
FR-PHO-09 When the photo is selected, resize handles shall be displayed. When a text block is selected, the handles shall be hidden. Must
FR-PHO-10 Photo rotation shall not be supported (rotation handle disabled). Must
FR-PHO-11 All photo data shall remain client-side. No image data shall be uploaded to any server. The photo shall be loaded via a browser Object URL. Must
FR-PHO-12 Object URLs shall be revoked when the photo is replaced, removed, or the application unmounts, to prevent memory leaks. Must

3.7 Export

IDRequirementPriority
FR-EXP-01 The user shall be able to export the finished card as a JPEG file via a prominently placed "Finish (Export JPEG)" button. Must
FR-EXP-02 The exported image shall be exactly 1500 × 2100 pixels regardless of the current viewport scale. Must
FR-EXP-03 The exported image shall be JPEG format at 95% quality. Must
FR-EXP-04 The exported image shall not include UI elements (selection boxes, guide lines, resize handles, card border stroke). Must
FR-EXP-05 The exported file shall be named with a timestamp: greeting-card-YYYYMMDD-HHmmss.jpg. Should
FR-EXP-06 Export shall trigger a browser download without navigating away from the page. Must

4. User Interface Requirements

4.1 Layout

IDRequirementPriority
UI-LAY-01 The application shall use a two-panel layout: a fixed-width controls sidebar on the left (300px) and a flexible canvas area on the right. Must
UI-LAY-02 The application shall fill the full browser viewport with no scrolling on the page level. The controls panel shall scroll independently if content overflows. Must
UI-LAY-03 Usage hints (drag instructions, keyboard shortcuts) shall be anchored to the bottom of the controls panel. Could

4.2 Controls Panel Organization

The controls panel shall be organized into the following sections, separated by horizontal dividers, from top to bottom:

  1. Header — Application title ("Card Designer")
  2. Photo controls — Add/Replace photo button
  3. Card Background — Background color picker with hex value and preview swatch
  4. Text block selector — Tab-style buttons to switch between Headline (A) and Message (B)
  5. Text properties — Text content, font size, font family, text color, alignment
  6. Display options — Safe margin toggle
  7. Actions — Reset Positions, Export JPEG
  8. Hints — Usage tips

4.3 Visual Design

IDRequirementPriority
UI-VIS-01 The interface shall use a clean, minimal aesthetic with a light gray workspace background and a white controls panel. Should
UI-VIS-02 Control labels shall be uppercase, small (12px), with letter-spacing, following a standard form-label pattern. Could
UI-VIS-03 The active text block tab and active alignment button shall be highlighted with a blue border and light blue background. Should
UI-VIS-04 The export button shall be visually prominent (filled blue, larger padding, bold text) to distinguish it from secondary actions. Should

6.2 Persistence

No data persistence is required. Card state exists only in browser memory for the duration of the session. Refreshing the page resets to defaults. The only output artifact is the exported JPEG file.

7. Rendering Layer Order

Content on the card shall render in the following order (back to front):

  1. Background color — Fills the entire card area
  2. Photo — Rendered on top of the background, clipped to card boundaries
  3. Text blocks — Rendered on top of the photo
  4. UI overlays (not exported) — Selection boxes, safe margin guides, resize handles, card border stroke
Note: The layering order is fixed. There is no requirement for the user to re-order layers. Text always appears above photos, and the background is always behind everything.

8. Constraints & Assumptions

8.1 Constraints

  • Only one card can be designed at a time (no multi-card workflow).
  • Only one photo can be placed on the card at a time.
  • Exactly two text blocks are available; the user cannot add or remove text blocks.
  • Card dimensions are fixed at 5″ × 7″ (1500 × 2100px). There is no option to change card size.
  • Export format is JPEG only.
  • Fonts are limited to system fonts; no custom font upload or web font loading.

8.2 Assumptions

  • Users have a desktop browser with HTML5 Canvas support (all modern browsers).
  • Users will print the exported JPEG themselves or use a third-party print service; the application does not integrate with any print provider.
  • Photo files uploaded by users are reasonably sized (a few MB). Very large images (50+ MB) may impact browser performance; this is acceptable.
  • System fonts are sufficient for the target audience; typographic variety is secondary to simplicity.

9. Acceptance Criteria

IDScenarioExpected Outcome
AC-01 User opens the application for the first time. A card is displayed with default headline and message text, light pink background, no photo, and no guide lines visible.
AC-02 User types new text in the text field. The corresponding text block on the canvas updates in real-time as the user types.
AC-03 User changes the font size slider. The text on the canvas resizes immediately. The numeric input stays in sync.
AC-04 User selects a different font family. The text on the canvas re-renders in the selected font.
AC-05 User changes the text color. The text on the canvas changes color. The hex value label updates.
AC-06 User changes the background color. The card background updates immediately. The hex value and preview swatch update in the controls panel.
AC-07 User uploads a photo. The photo appears on the canvas, scaled to card width, centered vertically. The "Add Photo" button changes to "Replace Photo". The photo is selected with resize handles visible.
AC-08 User drags a text block toward the edge of the card. The text block stops at the card boundary and cannot be dragged further out.
AC-09 User drags a photo partially off the card. The photo moves freely. The portion outside the card boundary is clipped (not visible).
AC-10 User presses Arrow Right, then Shift+Arrow Down. The selected element moves 1px right, then 10px down.
AC-11 User resizes the photo using the corner handle. The photo scales proportionally. It cannot be made smaller than 20×20px.
AC-12 User clicks "Finish (Export JPEG)". A JPEG file downloads. The image is 1500×2100 pixels and contains no UI overlays (no selection boxes, no guides, no resize handles).
AC-13 User selects the photo and presses Delete. The photo is removed. Selection returns to Block A. The button returns to "Add Photo".
AC-14 User clicks "Reset Positions". Both text blocks return to their default positions. If a photo is present, it returns to its initial centered/scaled position.
AC-15 User toggles "Show Safe Margins" on. Dashed red lines appear 75px inset from each card edge. They are not included in the exported image.

10. Glossary

TermDefinition
DPIDots per inch. 300 DPI is the standard resolution for commercial print.
Safe marginThe area inside the card edge that is guaranteed not to be cut during printing. Typically 0.25 inches.
Object URLA browser-generated URL (blob:// scheme) that references a local file in memory without uploading it.
Konva.jsA JavaScript library for HTML5 Canvas with built-in support for shapes, images, text, drag-and-drop, and transforms.
Arc pathAn SVG path segment that follows a circular arc, used for gently curving text.
Bezier pathAn SVG path segment defined by control points, used for smooth curves. A "wavy bezier" chains multiple bezier segments with alternating directions.
TransformerA Konva UI control that adds resize handles around a canvas object.
